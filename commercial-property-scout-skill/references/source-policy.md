# Source Policy

## 目的

本文件固定商业地产搜索中的“来源角色”和“软文降级规则”，避免每次任务重新讨论平台价值。具体平台的当前质量仍需按任务观察；机器可读初始权重见 `source-registry.json`。

## 1. Verification / Benchmark

包括项目官网、开发商、业主招商、物业招商、政府公开信息、大型专业机构的市场研究或其直接代理项目页。

用途：项目身份、物业类型、市场价格带、招商状态、官方商业条件、项目级核验。

限制：来源权威不等于某个第三方广告中的具体单元当前一定真实；机构市场平均租金也不能直接套用到不同等级/不同资产类型。

## 2. Primary Discovery

结构化程度较高、可以按楼盘/区域/面积/价格筛选的商业地产平台。具体平台必须按当前城市入口、任务适用性和实际可用性选择，不把某一城市的组合固化为通用默认值。

用途：建立第一版候选池、同楼盘报价样本、发现具体经纪库存。

## 3. Broad Discovery / High Verification Burden

安居客、58 同城以及大量本地聚合/经纪平台。

用途：街铺、小面积、非标办公室、转租、园区和地方中介库存补漏。

约束：最低价默认不作为市场基准；异常低价必须交叉验证。平台内存在真实房源并不意味着低价广告自动可信。

## 4. Lead-only

SEO 聚合页、自媒体文章、招商软文、短视频口播、论坛帖子、缺乏方法透明度的“排行榜”。

只能用于发现项目名、招商方、官网、地址或其他原始线索，不能独立支撑核心价格、可租状态或“平台真实性排名”。

## 软文识别

出现以下特征时，把内容降级为 `lead-only`：

- 全文几乎只有优点和招商联系方式；
- “十大平台/最佳楼盘”但无方法、样本和数据源；
- 大量品牌关键词堆叠；
- 没有作者、日期、样本、价格口径；
- 结论与页面商业利益高度一致；
- 中介/招商方自己发布，却包装成第三方测评；
- 只给“最低价/限时价”，不披露具体单元和条件；
- 多个站点内容高度同源，只更换标题或品牌词。

## 独立来源原则

同一经纪公司在不同域名、不同账号或聚合平台同步发布，可能仍是同一上游数据源。只有来源主体和信息生成链路真正独立时，才能视作独立交叉证据。

常见“非独立”情形：

- 同一联系人、同一电话、同一文案、同一图片水印；
- 不同聚合站抓取同一经纪数据库；
- 项目招商稿被多家 SEO 站点原样转载。

## 必查主源闸门

贝壳和链家必须作为两个独立的 `critical` / `primary_discovery` 来源写入每个任务的 `source_plan.json`，并在其他房源平台之前依次直接访问。不得把贝壳与链家混为同一来源，也不得用一个抵消另一个。

两者只有以下状态可解除闸门：

- `completed_with_results`：计划内搜索通道已达到覆盖深度并取得结果；
- `completed_zero_results`：平台可正常使用、计划内通道已完成，但没有符合条件的结果。

`blocked_login`、`blocked_captcha`、`access_limited`、`unavailable`、`planned`、`in_progress` 和 `skipped_with_reason` 均不能解除闸门。任一必查主源出现登录、验证、限流、页面超时、空白页、入口失效、筛选失灵或浏览器故障时：

1. 保留当前浏览器标签页、URL、截图和状态；
2. 停止访问其他房源平台、停止新增采集、停止评分和报告生成；
3. 告知用户具体故障及需要其处理的动作；
4. 等待用户明确确认恢复，再从该来源继续。

房天下、安居客、58、搜索引擎或任何其他来源都不能作为替代项解除闸门。只有用户明确授权跳过某个必查主源时，才可记录带用户原话的 `user_authorized_waiver`；不得自行决定豁免。

## 任务级来源优先级

除贝壳与链家的必查规则外，由 LLM 根据城市、物业类型、交易类型和当前可用性，从 `source-registry.json` 选择其他适用来源并写入 `source_plan.json`。

若 registry 为当前城市提供 `entry_urls`，优先使用该入口；否则从平台当前首页或站内“商业办公/写字楼”导航取得入口。不得凭记忆拼接或猜测子域名顺序。发生 404、空白页或连接错误时，先核对一次当前入口和最终重定向 URL，再判断为失效或访问受限。

贝壳和链家必须显式记录为两个独立必查主源；安居客、58、房天下等只能在两者完成后按任务需要作为补漏或补充发现源。

必须区分：

- `completed_zero_results`：已直接尝试平台但没有适用结果；
- `blocked_*`：登录、验证码或访问限制，需要用户介入；
- `planned`：尚未尝试；
- `skipped_with_reason`：可解释计划变更，但不计入已尝试覆盖；
- 搜索引擎未返回该站页面：只能说明公开索引无结果，不算平台尝试。

必查主源只有 `completed_with_results` 或 `completed_zero_results` 才可满足终态要求。其他 `critical` / `high` 来源受限时同样产生 blocker，不能靠替代来源自动消除。

来源“已完成”还要求其计划内搜索通道达到 `discovery-coverage-rules.md` 的深度或合法停止条件。只访问入口、只看首屏或只按用户偏好区域检索，均不得标记为覆盖完成。

若某个低证据来源占原始广告 65% 以上，触发集中度警告。仅由补漏/线索源支撑且未交叉核验的候选进入 `supplementary_lead`，不占主候选表；不要简单删除原始证据。

房源平台覆盖状态以用户可见浏览器的直接访问为准。后台抓取或搜索索引可提供辅助线索，但其验证码、登录提示、空白页或连接结果不得直接写成平台终态；需要在可见浏览器中复现后才能标记 `blocked_captcha`、`blocked_login` 或 `access_limited`。

如果出现以下变化，应更新 `source-registry.json`，不要仅在本次报告里口头覆盖：

- 平台商业地产频道大幅调整；
- 房源核验机制发生明显变化；
- 平台长期不可访问或库存显著减少；
- 新的垂直平台经多次任务验证后表现稳定；
- 某个平台持续出现高比例的过期、重复或低价引流模式。
